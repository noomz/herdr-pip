# 01 - What does the terminal observe stream deliver?

Live probes were read-only (`terminal session observe` and `pane get`/`pane list`); samples are in `/private/tmp/claude-501/-Users-noomz-Projects-Opensources-herdr/1fd4916e-5d03-4f89-ae6f-7029ef7981c3/scratchpad/pip/`.

## 1. Socket method, params, record shape

- **There is no JSON socket-API method for observe.** `socket-api.mdx` has no terminal-observe entry (grep for `terminal` only hits mouse/image text, lines 162/182). Observe is part of the binary same-install *client protocol* on the client socket: the CLI connects to `client_socket_path()`, does a `TerminalHello` handshake with `cols`/`rows`, requires the server to answer `RenderEncoding::TerminalAnsi`, then sends `ClientMessage::ObserveTerminal { target }` (`src/client/terminal_sessions.rs:73-126`, `:19-24`; `src/protocol/wire.rs:532-536`). Server flips the connection into `TerminalObserve` (`src/server/headless.rs:1303-1325`). For a plugin, the practical interface is the CLI: `herdr terminal session observe <target> [--cols N] [--rows N]` (`src/cli.rs:604-617`; docs `docs/next/website/src/content/docs/cli-reference.mdx:376-405`). Defaults 120x40 (`src/cli.rs:644-645`); each flag must be 1..=65535 (`src/cli.rs:690-700`). Target may be a pane, terminal, or agent id (cli-reference.mdx:397-398; `resolve_terminal_session_target`, headless.rs:1267). Unknown target -> server sends `ServerShutdown{reason:"terminal session observe failed: terminal target X not found"}` (headless.rs:1291-1297), which the CLI prints as `terminal.closed`.
- **CLI stdout record** (NDJSON, one per line), `src/client/terminal_sessions.rs:132-145`:
  `{"type":"terminal.frame","seq":u64,"encoding":"ansi","width":u16,"height":u16,"full":bool,"bytes":"<base64 STANDARD>"}`.
  Stream end: `{"type":"terminal.closed","reason":<string|null>}` (:147-156); plain EOF (`UnexpectedEof`) ends silently with no closed record (:159). Graphics messages are dropped (:157), so kitty images are not delivered.
- Wire struct `TerminalFrame { seq, width, height, full, bytes }` ("Terminal escape bytes ready to write directly to stdout"; `seq` is monotonic per client) - `src/protocol/wire.rs:1324-1337`.
- **Frames are ANSI repaint bytes generated from a server-side rendered cell grid, not raw PTY bytes.** The server renders the pane's libghostty state into a ratatui buffer (`render_terminal_virtual`, `src/server/render_stream.rs:578-609`, called from `src/server/headless/render.rs:~790`) and a `BlitEncoder` diffs it into CUP/SGR escapes (`src/protocol/render_ansi.rs:58-142`). `full` = repaint requested, or no previous frame, or size changed (render_ansi.rs:92-94); otherwise it is a diff of changed cells.
- **First frame is a full repaint** (`prev.is_none()` -> full; `reset_baseline` on observe start, headless.rs:1315) and additionally starts with `ESC[2J` (clear_before_full_redraw = no previous frame, render_ansi.rs:95). Observed: `seq 1 full=true`.
- Decoded sample (pane `wC:p7A`, `--cols 40 --rows 10`, frame seq 1, 585 bytes, first 330):
  `ESC[?2026h ESC[?25l ESC]8;;ESC\ ESC[2J ESC[1;1H ESC[0;39;49m "->" ESC[1;2H " Syncing bundled skills to all profiles" ESC[2;1H "  default: ~1 user-modified     " ESC[3;1H (40 spaces) ... ESC[0m ESC[10;40H ESC[?25l ESC[?2026l ESC[10;40H ESC[?25l`. Whole frame is wrapped in synchronized-output `?2026h ... ?2026l`; every cell row is padded to full width with spaces; output is truecolor SGR (`38;2;r;g;b`) plus OSC 8 hyperlink resets.
- Incremental sample (pane `wC:p9A`, 100x63, seq 2, `full=false`, 93 bytes): `ESC[?2026h ESC[?25l ESC]8;;ESC\ ESC[63;100H ESC[0;38;2;147;153;178;49m "1" ESC[0m ESC[54;3H ESC[?25h ESC[?2026l ESC[54;3H ESC[?25h` - a single changed cell, then cursor placement.

## 2. `--cols` / `--rows` semantics (decides the popup design)

- **No source resize.** `--cols/--rows` only become the observer's own `client.terminal_size` via the handshake (`clamp_terminal_size`, `src/server/client_transport.rs:558-562`, applied at :~722) and later `ClientResize` events; for `TerminalObserve` the resize handler updates only that client's `terminal_size`/`cell_size` and requests a repaint (`src/server/headless.rs:2208-2224`). Only `TerminalAttach` (control mode) calls `runtime.resize(...)` (headless.rs:2194-2206). Empirically: `herdr pane get wC:p7A` before/after observing at 40x10 -> identical JSON (viewport_rows 32 unchanged); observing `wC:p9A` at 100x63 also left `viewport_rows` at 63. (`pane get` exposes rows only, not cols; the code path above covers cols.)
- **It is a CROP, not a re-render at that size.** The server calls `runtime.render(frame, Rect(0,0,cols,rows), true)` (render.rs:~786, render_stream.rs:578-583) which copies source cells row-by-row from the **top-left** of the source viewport, stops at `area.height`/`area.width`, and blanks the remainder (`src/pane/terminal.rs:2406-2441`). No reflow, no scaling, no scrolling to the bottom. Probe confirms: source `wC:p7A` is 32 rows; observed at 40x10 it returned the first 10 rows of the viewport, each truncated to 40 columns ("Update complete! (v0.22.1 -> v0.22.2) [" is cut mid-line) - while `herdr pane read wC:p7A --source visible` shows the full lines.
- Cursor: drawn only if it lies inside the crop area (terminal.rs:2444-2452); also hidden when the source is scrolled back (render_stream.rs:599).
- Consequence: the popup can request frames at its own size without its own emulator, but it only ever sees the **top-left window** of the source viewport. A source taller than the popup loses its bottom rows (where prompts/status usually live).

## 3. Rate, coalescing, quiet panes, alt-screen, scrollback, end of stream

- **Rate/coalescing:** server renders are gated by `MIN_RENDER_INTERVAL = 16 ms` (`src/app/mod.rs:39`, `src/server/headless/render.rs:13,29`), so at most ~60 frames/s, with PTY output within a window coalesced into one frame; identical frames are skipped (`blit_encoder.is_current`, render_stream.rs:~96-100). Observed on a busy Claude pane: 7 frames in ~6 s.
- **Quiet panes:** no frames after the initial one (probe of idle `wC:p7A`: exactly 1 line in 3 s). Docs: quiet panes do not trigger the stall timeout (cli-reference.mdx:402-403).
- **Surprise - repeated full frames:** on `wC:p9A` (a Claude pane that uses synchronized output) frames 3-7 were all `full=true`, 19,164 bytes each (vs 93 bytes for the one diff). When the pane is inside `?2026` sync mode the server calls `request_recompute()` -> `request_repaint()` for the observer (render.rs:~775-781, 795-801; render_stream.rs:76-85), forcing a full repaint on the next frame. Treat "full=false" as an optimization, not a guarantee; budget for ~20 KB/frame at 100x63 (~6 KB estimated at popup size).
- **Sync output:** the server holds back frames while the source is mid-synchronized-output (render.rs:~774-781), and emits its own `?2026h/l` wrapper around each frame.
- **Alt-screen:** the renderer reads libghostty's current render state for whatever screen is active, so alt-screen apps render like any other grid (inferred from `render_state.update`, terminal.rs:2372-2379; not separately probed). No scrollback exists to deliver.
- **Scrollback:** only the source's current viewport is rendered. If the user has scrolled the source back, the observer shows that scrolled view (cursor hidden). Observer cannot scroll or take input (cli-reference.mdx:400-401).
- **Termination:** server shutdown/detach/terminal-gone -> `ServerShutdown{reason}` -> `terminal.closed` (terminal_sessions.rs:147-156; headless.rs:1703-1713 "detached"; render.rs:~762 "terminal attach ended: terminal X not found"). On Linux/macOS an observer whose socket write makes no progress for **30 s** (`OBSERVER_WRITE_TIMEOUT`, `src/server/client_transport.rs:45`, set at :1072-1082) is dropped, possibly with no `terminal.closed` (cli-reference.mdx:402-404); the pane keeps running. A slow reader just needs to keep draining stdout. Note a rendering-stalled observer's frames are deferred (`DeferredRender`, render.rs:~563-571).

## 4. Smaller-viewport display without a VT parser

Frames are already cell-grid repaints at the **observer's requested size**, so no VT parser/emulator is needed in the plugin. The cheapest path: spawn `herdr terminal session observe <pane> --cols C --rows R` with C/R = popup interior size, base64-decode each `bytes` field, and write the raw bytes to whatever terminal surface displays the popup (e.g. a viewer process running inside the popup pane, whose stdout herdr's own emulator interprets). CPU is dominated by the server's per-frame render (bounded to C x R cells) and base64+JSON on a ~20 KB/frame worst case. A `vt100`/libghostty parse in the plugin is needed only if the plugin must composite the frame into its own UI (overlay/border) or show the *bottom* of a tall source - which this protocol cannot deliver (crop is top-left only).

## Implications for the peek renderer

- Spawn `herdr terminal session observe` (no JSON socket method exists) with the popup's interior size; decode `bytes` and write straight to the display - no emulator needed for plain mirroring.
- Opening cost is free to the source: observing never resizes or steals input; multiple observers are allowed. Re-send `--cols/--rows` by restarting the process (the CLI exposes no resize command in observe mode; the server handles `ClientResize` for observers but the CLI never sends it).
- Crop is top-left: a source taller/wider than the popup is truncated, not scaled or bottom-anchored. Decide: size the popup to the source (rows/cols from `pane get`/`pane list` `scroll.viewport_rows`), or accept truncation, or fall back to `herdr pane read <id> --source visible` + tail slicing for a bottom view.
- Handle `ESC[2J` at start, `?2026h/l` wrappers, `?25l/?25h` cursor toggles in the byte stream; hide or ignore cursor if drawing a custom frame.
- Expect repeated `full=true` ~20 KB frames from sync-output apps (Claude, etc.); throttle/coalesce on the consumer side if needed.
- Treat `terminal.closed` and EOF (no record) both as end-of-stream; keep reading continuously to avoid the 30 s write-stall disconnect.
